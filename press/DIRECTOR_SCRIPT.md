# 拍簿 — 影片素材導演腳本

> **這份檔案是所有影片／動態素材的唯一需求來源。**
> 要改任何一段演示，**先改這裡**，再照著改實作。
> 這樣才不會在新一輪修改中，不小心把舊版本要求過的細節弄丟。
>
> 涵蓋兩個產出：
> - **官網首頁的實錄示範影片**（`site/assets/shots/*_demo.mp4`）
> - **商店預覽影片**（Remotion，`site/press/remotion/`，輸出到 `store_assets/`）

---

## 0. 不可退讓的前提（每次重錄都要重新確認）

| # | 規則 | 為什麼 |
|---|---|---|
| P1 | 素材一律是**實機真實操作錄影**，不是模板重刻、不是靜態圖加緩慢放大 | 商店預覽的說服力全部來自「這真的是 App 的樣子」。投影片式的 Ken Burns 一眼就看得出是拼湊的 |
| P2 | 打包必須是**正式商店狀態**：`dart_defines.store.json`（**不含** `PIBOOK_DEV_TOOLS`） | 帶開發者旗標時相似組標題會多一顆實驗 icon（複製相似報告），使用者已回報過 |
| P3 | 示範用的照片／影片必須是**一般人真的會拍的東西**：人像、多人聚會、狗貓、表演、煙火、食物、風景 | 樣板圖庫感會讓人覺得是假的 |
| P4 | **素材不得有裸露**（泳裝、裸上身一律不用） | 商店審查與品牌調性 |
| P5 | 錄影前先確認**資料狀態符合演示情境**：要示範「加入相簿」，被示範的照片就必須還沒被加入過任何相簿 | 使用者回報過「有些照片你稍早已經示範加入過了」 |
| P6 | 兩種尺寸（886×1920 App Store／1080×1920 Play）**各自渲染一次**，禁止「渲染一支再裁另一支」 | 長寬比 0.461 vs 0.5625，裁出來一定切掉上下一大塊 |
| P7 | 錄影素材一律 **1080p / 30fps / 6 Mbps**，重量級影片先換成輕量版再錄 | 模擬器的瓶頸是**影片解碼**不是繪製；85Mbps 素材會讓錄影掉到 8.9fps |

## 1. 商店預覽影片（Remotion）

### 1.1 整體風格

- **現代、簡約、年輕、有節奏感。** 不要傳統企業宣傳片的慢節奏。
- **不使用壓在畫面上的字幕。** 每個功能都是：**滿版動態標題卡 → 實機操作畫面**。
- 標題卡：滿版單色 + 大字彈簧推入，字要在 0.6 秒內全部落定（卡只有 1.4 秒，慢了就讀不完）。
- 每段有自己的色票（見 `src/theme.ts` 的 `ACCENTS`）。
- 開場品牌卡、結尾承諾卡各一張，形成亮 → 彩 → 暗的收束。
- 規格：30fps、H.264、**一定要有音軌**（App Store 硬性要求，靜音 AAC 可）、15–30 秒。

### 1.2 三條鏡頭語言的鐵則

| # | 規則 | 為什麼 |
|---|---|---|
| C1 | **標題卡切到實機畫面後，動作必須在 ~0.3 秒內開始。** 不要先停在靜止畫面等好幾秒 | 停太久使用者 get 不到這一幕要傳達什麼 |
| C2 | **要介紹的細節必須主動聚焦。** 用推近／平移／局部高亮把使用者的視線帶到目標上（例：相簿軌、縮圖上的整理標記） | 只是把整個畫面播出來，使用者不知道該看哪裡 |
| C3 | **不要用「整段緩慢放大」當運鏡。** 連續的次像素縮放會讓畫面邊緣抖動閃爍，而且是投影片的老套感 | 使用者實際回報過邊線抖動 |

> **C3 的實作要求**：圓角遮罩與陰影掛在**完全不動**的外層 div 上，
> 動的是內層。外框不動 → 邊緣永遠不會抖。運鏡改成
> 「停 → 一次彈簧推近／平移 → 停」的分段式，不是每一幀都在變。

### 1.3 分鏡表

順序固定為：開場 → 01 整理 → 02 歸檔 → 03 挑最佳 → 04 省空間 → 05 回憶 → 06 圖庫 → 結尾。

#### 開場（~2.1s）
品牌 icon 彈入、字標裁切推出、兩行標語。兩道色帶橫掃避免靜態感。

#### 01 整理 ORGANIZE
**標題卡**：滑一下／就整理好一張

**實機分鏡（必須包含全部四拍，這是完整傳達功能的最低要求）**
1. 右滑保留第 1 張 — 快
2. 右滑保留第 2 張 — 快
3. **下滑丟棄第 3 張** — 必須有，否則使用者只看到「保留」，不知道這是雙向決定
4. 右滑保留第 4 張

**要點**
- 第一次滑動**不可以卡頓**。錄影前先讓該畫面完全穩定（縮圖到齊、動畫停止）再開錄。
- 節奏是「真人操作的速率」：滑動本身順暢，張與張之間留 0.3–0.6 秒的短間隔，可有輕微隨機性。
- 不要快到看不清楚卡片飛出的方向。

---

#### 02 歸檔 FILING
**標題卡**：點一下相簿／照片就收進去

**實機分鏡**
1. 連續示範 **3 張以上**的歸檔，不是只有一次
2. 每一次點擊都要有**強烈、顯眼、直觀**的觸控指示效果
3. 相簿軌在畫面底部 → 用**運鏡把視線帶到底部相簿軌**，讓使用者看懂「他點的是下面那一排相簿」

**要點**
- **每張照片必須進到內容上合理的相簿**（聚會 → 家人朋友、食物 → 美食、風景 → 旅行、貓狗 → 毛小孩）。
  相簿軌的順序**每張照片都不一樣**（App 會依內容推薦），所以錄製腳本必須
  **先讀畫面（uiautomator）再照名字點**，不可以用固定座標。
- 觸控指示效果的時序見 §3。

---

#### 03 挑最佳 BEST SHOT
**標題卡**：連拍裡最美的／自動挑好

**實機分鏡**
1. 稍微下滑列表
2. 對**兩組**相似照片各點一次「保留」（從每組裡挑一張按保留）
3. 點進下一組的第一張，**放大進入全螢幕比較介面**
4. 在全螢幕裡**往左、往右滑動比對**同一組的照片

**要點**
- 節奏快，但不能快到看不清楚在操作什麼。
- **不要點進「相似組 3」看全螢幕**：那一組的照片放到滿版會有服裝上的疑慮（見 P4）。
  目前是點進「相似組 2」（情侶在觀景台的兩張）。

---

#### 04 省空間 FREE SPACE
**標題卡**：三部影片／省回 1.7 GB

**實機分鏡**（要讓使用者一眼看懂「選好 → 開始 → 跑完就好了」）
1. 實際**勾選影片**（三部）
2. 按「下一步：選擇壓縮品質」
3. 在品質清單上比較「高品質保留 / 平衡 / 極致省空間」，選回推薦的平衡
4. 按「開始壓縮」→ 確認對話框 →「開始」
5. 壓縮進行中的畫面**只留一小段**（正在壓縮影片 · 1/3）

**要點**：每個步驟的畫面都要出現，但剪接節奏要快 ——
實作上是把三段（選取／挑品質／開始跑）之間的空檔剪掉再接起來，
接點都落在同一個畫面狀態上，所以看不出剪過。

> ⚠️ **模擬器跑不完整段壓縮。** 實測（2026-08-31）不論選幾部、選哪個品質，
> 都會回到品質頁並跳出「N 部壓縮失敗」—— 模擬器的 MediaCodec 編碼器吃不下
> 這些來源。要拿到真正的**完成結算畫面**只能在實機上錄。
> 在那之前，這一拍**刻意停在「開始跑」的瞬間**，數字由標題卡負責交代；
> 不做假的完成畫面。
> （另外：免費額度是每天 3 部，超過會擋在 Premium 付費牆；
>  「用整理換 Premium」的天數要**登入**才領得到，所以也繞不過去。）

---

#### 05 回憶 MEMORIES
**標題卡**：留下的照片／自己回來找你

**實機分鏡**
1. 進畫面後**很快就往上滑到下一部影片**
2. 連續往下滑，讓人感覺得到「像短影音一樣一部接一部」
3. 中間穿插**雙擊畫面標記愛心**

**要點**：不可以整段都停在第一部影片。重點是「可以一直滑下去」這件事本身。

---

#### 06 圖庫 LIBRARY
**標題卡**：整理過的／一眼看得到

**實機分鏡**
1. **聚焦運鏡**：推近到縮圖，讓使用者看清楚每格上的**整理標記**（左上角的點）與**相簿標記**（右上角的數字）
   —— 這是手機內建相簿做不到的事，是我們的優勢，必須讓人看見
2. 對某張照片**長按**呼出浮動選單
3. 點「加入相簿」→ 跳出相簿清單
4. 把照片加入合適的相簿

#### 結尾（~2.6s）
深色底、「照片／不離開你的手機」、icon + 拍簿 + PIBOOK.APP。

## 3. 觸控指示效果（後製疊加）的規格

`show_touches` 在 `screenrecord` 的輸出裡**完全不會出現**，所以觸控指示一律是後製疊上去的。

### 時序（使用者連續回報過兩次「慢半拍」）

```
   -0.10s ── 指示圈開始出現（預備：外圈擴散、透明度上升）
    0.00s ── 接觸瞬間：實心點 + 白色光暈最亮、最大
   +0.30s ── 收掉
              ↑ App 的畫面反應（相簿列高亮、卡片飛走）落在這之後
```

**判準：使用者必須先看到點擊效果，然後才看到 App 反應。** 順序反了就是錯的。

### 實作

`scratchpad/taps.py`。每個指示圈給一組 `{xy, roi, win, hold?}`：
`roi` 是要盯的畫面區域、`win` 是搜尋的時間窗、`hold` 是長按的持續秒數
（長按會多畫一圈順時針填滿的進度環）。

**時間窗要各給各的、不要全域取前 N 大** —— 片段裡的捲動與滑動比按鈕反應大得多，
全域取極值會全部選到滑動。

### 為什麼不能只靠 taplog 的時間戳

`input tap` 發出的時刻與**錄影檔的時間軸**之間有一個常數偏移（錄影啟動時間）。
只用 taplog 對時，整批指示圈就會系統性地晚半拍。

**正確做法**：錄完後從影片本身量出 UI 反應的起始幀（逐幀差分找變化起點），
用「第一個 tap 對應到第一個變化起點」算出常數偏移 δ，再把整批指示圈往前對齊。
指示圈的接觸瞬間要落在**變化起點之前約 2 幀**。

### 外觀

- 夠大、夠顯眼：外圈直徑約 140px（1080 寬的畫面上），不是細細的一圈。
- 白色光暈 + 深色內圈的雙層構造，白底 UI 與深色照片上都看得見。
- 擴散環 + 實心點同時存在，實心點在接觸瞬間最實。

### 長度：兩支，不要為了 Apple 的上限犧牲另一支

| 版本 | 長度 | 給誰 | 為什麼 |
|---|---|---|---|
| `long` | ~46s | Google Play / YouTube | Play 的宣傳影片是 YouTube 連結，**沒有長度上限** |
| `short` | ~29.5s | App Store | Apple 規定 App Preview **必須 15–30 秒**，超過直接退件 |

以前兩邊共用一支 30 秒，結果是整支被壓得太趕（開場字卡不到一秒就切走）。
現在 `short` 不是「把長版加速播」（那只會更趕），而是**每段各自取較短的素材窗** ——
留住那一拍的重點動作，捨掉前後的鋪陳。

### 模擬器：錄影前先確認記憶體

`~/.android/avd/<name>.avd/config.ini` 的 `hw.ramSize` **只吃純數字（MB）**。
寫 `8G` 會被當成無效值**默默退回 2048**，而且沒有任何警告 ——
實測 guest 只剩 **178 MB 可用**，App 一直 GC、錄起來每一段都掉幀。
改成 `8192` 之後 free 從 178 MB 變成 5.8 GB，回憶那段的實拍幀率從 10.6 fps 升到 26.8 fps。

啟動時也把參數寫明，不要只靠 config：

```bash
emulator -avd <name> -memory 8192 -cores 6 -gpu host -no-snapshot-load -no-boot-anim
```

### 壓縮：現在錄得出完整流程了（曾經是 App 的 bug）

`entity.originFile` 給的是 `/storage/emulated/0/...` 這種公開路徑。範圍儲存下
媒體檔在磁碟上是 `u0_a191:media_rw 0660`，**stat 允許、open 拒絕** ——
而 App 用 `exists()` 判斷，於是把一條開不了的路徑交給 ffmpeg，
ffmpeg 印完版本橫幅就以 `Permission denied` 收工。
更難查的是 App 只記錄 log 的**最後 500 字**，剛好切在橫幅上，看起來像「編碼器壞掉」。

修法：拿 `entity.getMediaUrl()` 的 content URI 換成 ffmpeg-kit 的 `saf:` 輸入（背後是 fd），
不必先複製幾百 MB。硬體 MediaCodec 那條路沒事，**只有退回 ffmpeg 的軟體路徑會踩到**，
而退回是常態 —— 真機上只要遇到一顆不服從碼率的編碼器就會全軍覆沒。

錄製時還有兩個閘要先過：
- **免費額度每天 3 部**，測試用掉就會跳付費牆 → 把裝置日期往後推一天。
- MediaStore 用 `scan_file` 建的列是 `is_pending=1`、**App 看不到** →
  只能 `pm clear com.google.android.providers.media.module` + `scan_volume`。

### 三個錄製上的坑（都踩過）

1. **`input swipe` 的捲動距離不固定** —— 快速滑會帶 fling，同一段腳本每次停的位置不同，
   後面照固定座標點就會點空。**用 600ms 的慢速 swipe**，實測連跑三次位置完全一樣。
2. **`input tap` 連下兩次不算雙擊** —— 每次 `input` 都是一個新行程，間隔常常超過
   300ms 的雙擊窗。要用 `input tap x y & sleep 0.10; input tap x y`（第一發丟到背景）。
3. **相簿軌的順序會隨「最近用過」改變** —— 錄之前先乾跑一次把實際座標量出來
   （`scratchpad/probe.py`），再用固定座標重放；重放前記得把乾跑用掉的照片
   用「復原」還原（實測復原也會把推薦順序一起還原）。

## 5. 錄製環境

- 模擬器：1080×2400，`adb shell screenrecord --bit-rate 6000000 --size 1080x2400`
- 狀態列固定：sysui demo mode（時間 9:41、滿格訊號、滿電）
- 錄影前把重量級影片換成輕量版，錄完再換回來（見 P7）
- 裝置日期固定在 `2026-08-30`，讓「今天／這幾天」的照片分組成立
- release build 在模擬器上要暫時關掉 Impeller（`android/app/src/release/AndroidManifest.xml`），**build 完立刻刪掉**

| `site/press/remotion/src/AppPreview.tsx` | 每一段的起點、長度、播放速率、運鏡、聚焦圈 | 跟著 repo |

其餘四段（review / album / similar / memory）在 `clips/` 裡存的**就是完整錄影**，沒有被剪短。

### 依成本由低到高

**幾乎不花成本 —— 只改 `AppPreview.tsx` 的數字再 render：**
- 某段太長／太短 → 改 `stageFrames`
- 某段從太早／太晚開始 → 改 `startFrom`
- 某段節奏太快／太慢 → 改 `rate`
- 運鏡推到哪裡、停多久 → 改 `moves` 的 `rect` 與 `at`
- 聚焦圈的位置、時機 → 改 `highlights`
- 標題卡的字 → 改 `lines` / `highlight`
- 段落順序 → 調整 `BEATS` 陣列順序

> 這一類最好的問法是**指出時間點與想要的結果**，例如
> 「00:12 那段停太久，砍掉一秒」「圖庫的圈再晚半秒出現」。
> 我直接改數字重跑，不需要重看素材。

**中等 —— 要動 ffmpeg 重剪，但仍不必開模擬器：**
- 想改 `library` 或 `compress` 的剪點 → 從 `raw/` 重剪（指令範本在 `raw/README.md`）
- 想把某段的某個片刻剪掉／換順序

**最貴 —— 一定要重新錄影：**
- 演示的**操作內容**要變（例如多滑一次、換一個相簿、換一張照片）
- 畫面上的**數字**要變（整理張數、省下多少 GB、相似組數）
- 換語系（App 的 UI 語言）

> 重錄需要：把模擬器叫起來、還原示範圖庫與整理狀態、逐步驗證座標。
> 這是整個流程裡最花時間的部分，**能用剪的就不要重錄**。

### 一件現在還缺的

**壓縮的「壓縮中 → 完成慶祝」拍不出來** —— 模擬器的編碼器不聽位元率指令，
App 退回 libx264，而打包進去的 ffmpeg 一啟動就錯誤退出（見 §1.3 的 04 段）。
這一段要補，只能在**真機**上錄一次。
